## Integración

El Broker existente ofrece una herramienta `projects`: listar/resolver nombres y alias, proponer una carpeta, guardar objetivos/requisitos/decisiones, crear y revisar tareas pendientes, enlazar/desenlazar dependencias, despachar Engineering e inspeccionar estado, intentos, comentarios y artefactos. `activity` responde qué trabajo tiene Engineering entre proyectos sin cargar sus historiales.

La autoridad es el registro nativo de **Hermes Projects y Kanban**, en el hogar explícito `~/.local/share/argos-hermes-pilot/state/projects`. Se mantiene separado del hogar conversacional; no se copian tareas ni conversaciones a una base propia de ARGOS. El brief usa un sobre JSON acotado en el campo nativo `Project.description`, como estaba previsto. Los estados, dependencias e intentos permanecen en las tablas y API nativas. No hay otro planificador, bucle de agentes ni sistema de memoria.

La primera autorización muestra propósito, carpeta y alcance de código/pruebas en la revisión gráfica existente. Solo la ruta de usuario del Broker puede confirmarla. Repetir exactamente una creación ya autorizada recupera el mismo proyecto sin pedir otra aprobación; las actualizaciones ordinarias dentro del alcance se ejecutan directamente. Una petición hipotética no crea proyectos. La autorización pendiente caduca y no sobrevive al reinicio; una autorización ya registrada sí.

Los proyectos no dependen de un ID de conversación. General los resuelve dentro de su turno habitual, recuperando solo el brief elegido y evidencia acotada de sus tareas. Una referencia ambigua devuelve candidatos; no establece un modo global de especialista. Las operaciones deterministas no consultan otro modelo.

Las modificaciones exigen la revisión actual. La actualización del brief comprueba y escribe el campo nativo bajo una transacción `IMMEDIATE`: la API del pin no ofrece un parámetro CAS, por lo que esta operación usa el mismo campo/esquema nativo directamente. No añade tablas. Las demás mutaciones usan las API nativas, serializadas entre procesos del adaptador. La creación parcial conserva su intención en el proyecto nativo y puede reconciliar carpeta/tablero sin sobrescribir archivos ajenos.

Engineering recibe objetivo, brief vigente, alcance, carpeta y criterios de verificación en el cuerpo de su tarea. Las tareas quedan pendientes hasta un despacho explícito. Una tarea aún no iniciada puede actualizarse; una que ya tuvo ejecución conserva ese contexto y requiere un seguimiento si cambian los requisitos. Una versión antigua del brief no se despacha silenciosamente.

Cada proyecto tiene un perfil Engineering y una política fija derivada del bloque A. El adaptador importa su lanzador validado; el propietario y el despacho siguen siendo nativos. Se permite un trabajo Engineering simultáneo, con límite nativo de 300 segundos y presupuesto de fallos acotado. No hay despacho automático al abrir ARGOS ni al recuperar un intento interrumpido. Cerrar la conversación o el Broker no cancela el trabajador nativo.

## Instalación y límites

La instalación actual tiene Projects habilitado. En otra instalación preparada con las dependencias y la reparación de A:

```sh
python scripts/prepare_hermes_pilot.py --projects on
# Deshabilitar la herramienta sin borrar proyectos ni cancelar trabajo:
python scripts/prepare_hermes_pilot.py --projects off
```

La activación comprueba el pin y la reparación nativa; no inicia inferencia ni trabajadores. `installation.json` conserva raíces, dispositivo de voz y rutas propias de cada equipo. El valor predeterminado para instalaciones nuevas sigue siendo desactivado. Las pruebas nativas se ejecutan con `python ~/.local/share/argos-hermes-pilot/projects/qa.py`; `live_check.py` y `security_check.py` son pruebas explícitas que consumen la suscripción y crean fixtures.

El estado `review` significa revisión pendiente, no aceptación automática. Los hashes de artefactos corresponden a archivos observados ahora; las afirmaciones del trabajador no certifican pruebas ni una versión futura. La aceptación de hitos utiliza la vía confiable nativa: esta herramienta no concede autoaprobación, ni expone un botón para declarar una tarea terminada. Tampoco habilita red de comandos, instalaciones, publicación, impresoras, lanzamiento arbitrario de aplicaciones o ampliación de alcance.

Los propietarios de las pruebas quedaron detenidos, sin intentos abiertos, y se retiraron sus copias derivadas de autenticación. La sesión principal del piloto se conserva. El Core operacional, voz, modelos, ruta CUDA, navegador, aplicaciones y mantenimiento conservan sus implementaciones. La extensión firmada de Firefox sigue pendiente de traslado. Por decisión del usuario, **la latencia de esta CPU no es un criterio de aceptación**: este equipo prepara el desarrollo para el principal.
